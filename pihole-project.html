01 — The Problem

What's actually happening
on my home network?

Every device on a home network is constantly talking — smart TVs phoning home to ad networks, apps sending telemetry, trackers following you across the web. Most people have no visibility into any of it.

I wanted to change that. Not just block the noise, but understand it — see which devices were making unusual connections, detect abnormal behavior, and get a clear picture of what my network was doing at all times.

The question I was asking: If a device on my network suddenly starts behaving differently — making hundreds of DNS queries it wasn't making before — how would I even know? And what would I do about it?

02 — Layer 1

Pi-hole — DNS sinkhole
for the entire network

Pi-hole acts as the DNS resolver for my entire network. Every DNS query from every device flows through it. When a device tries to reach a known ad server or tracker, Pi-hole returns nothing — the request is sinkholes before it ever leaves my network.

The result: network-wide ad blocking with no client software — works on every device automatically, including smart TVs, phones, and IoT devices that can't run browser extensions.

03 — Layer 2

Suricata — intrusion detection
with custom rules

Pi-hole handles DNS filtering, but it can't detect behavioral anomalies in real-time. For that, I added Suricata — an open-source network IDS that inspects traffic at the packet level.

I wrote custom rate-based rules targeting three specific threat patterns I care about: DNS query spikes, TLS connection bursts, and SYN floods originating from a single host.

04 — Layer 3

The Spike Correlator —
what I built on top

Suricata fires an alert when a rule trips. But an alert alone doesn't tell you what the device was doing when it spiked. That's the gap I built eve_watcher.py to fill.

The tool continuously tails Suricata's eve.json log. When a spike alert fires, it looks back 60 seconds in the event stream and extracts every DNS hostname and TLS SNI the alerting device contacted — then packages it all into a structured JSON report.

Why SNI matters: TLS traffic is encrypted, but the Server Name Indication field in the TLS handshake is sent in plaintext. That means even for HTTPS connections, I can see exactly which hostname the device was connecting to — without decrypting anything.
eve_watcher.py — core logic
# Tail eve.json and watch for spike alerts def tail_and_correlate(eve_path): with open(eve_path) as f: f.seek(0, 2) # seek to end while True: line = f.readline() if not line: time.sleep(0.1); continue event = json.loads(line) # Spike alert fired — start correlation if event.get("event_type") == "alert": src_ip = event["src_ip"] ts = event["timestamp"] # Look back 60 seconds in event log for this host contacts = correlate_window( src_ip, ts, window_seconds=60 ) # Save structured report save_report(src_ip, ts, contacts)
05 — Engineering Decisions

Why I built it
this way

Why Suricata instead of raw packet parsing?

Suricata handles the hard parts — packet reassembly, protocol parsing, high-speed capture. Building that from scratch in Python would have been thousands of lines and still slower. By sitting on top of Suricata's structured eve.json output, my correlator only needs to handle business logic.

How are thresholds tuned?

I observed baseline traffic on my network for several days and measured real query rates per device. The thresholds (100 DNS/60s, 50 TLS/30s, 200 SYN/10s) were chosen to sit well above normal peaks but below patterns that would indicate actual anomalous behavior — updates, video calls, normal browsing all pass through without tripping alerts.

The encryption boundary: SNI (Server Name Indication) is visible in TLS handshakes because the client sends the target hostname in plaintext before the encrypted session is established. The correlator captures this — but reads nothing inside the encrypted payload. No decryption, no MITM.
